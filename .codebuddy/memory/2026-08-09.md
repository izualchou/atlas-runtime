- `<pids>` 和 `<tids>` 使用字符串名称（`prof_time,prof_event,prof_state`）→ 全部替换为数字 ID（`1001,1002,1003` 和 `2001,2002,2003,2004`）

  - Profile 2: `1002` → `2003` (Task 通用触发)
  - Profile 3: `1003` → `2002` (Task WiFi切换)
- 修复文件: atlas_trigger.prj.xml, profile_time.xml, profile_event.xml, profile_state.xml

#### 类别 B: 非标准 Tasker XML 标签（6 处）
- **Time 上下文**（3 处）：`<Repeat>0</Repeat><From>535</From><To>535</To>` → `<fh>8</fh><fm>55</fm><th>8</th><tm>55</tm>` — 旧版 Tasker 使用分钟-from-midnight 格式，现代版本要求 fh/fm/th/tm 格式

- 注：`<plugin.EB state="2">` 经核实确为 Tasker 对 Event Behaviour 插件的标准 XML 格式，非自定义标签
- 修复文件: atlas_trigger.prj.xml, profile_time.xml, profile_state.xml, profile_event.xml

## supervise/status bad format 诊断与 deploy.sh 修复 (2026-08-09, 第二次)

### 问题
`sv-enable atlas-runtime` 失败，`supervise/` 目录下 control、ok、status 三个文件大小均为 0。

### 根因
同日早前的 "supervise/ok 缺失修复" 引入了一个严重错误：使用 `touch` 预创建 `supervise/control` 和 `supervise/status` 作为普通空文件。但 runit 对这些文件有严格的类型要求：
- `supervise/control` 必须是 FIFO (命名管道)，由 runsv 通过 mkfifo() 创建。touch 创建的普通文件导致 sv 命令无法与 runsv 通信。
- `supervise/status` 必须是二进制格式状态文件（18 字节头部 + 服务名）。0 字节空文件被 runsv 读取时报告 "bad format"。
- `supervise/ok` 可以是普通空哨兵文件，但被前两个污染牵连。

### 修复方案
**deploy.sh 服务端修复**（3 处改动）：
1. 步骤 9：删除手动 supervise 目录创建 → 改为主动清理残留 supervise 目录，由 runsv 自动创建
2. 步骤 13：删除 "防流失" 的 supervise 重建逻辑 → 改为 runsvdir 存活检测 + 二次清理残留 + 两步残留进程终止 + `file` 命令类型验证
3. 结束区：增强诊断提示（包含 `file` 检查 control 是否为 FIFO）

**用户侧即时修复**（无需重启 Termux，前提是 runsvdir 仍在运行）：
```
sv down atlas-runtime; sv-disable atlas-runtime
pkill -f "runsv.*atlas-runtime"
rm -rf $PREFIX/var/service/atlas-runtime/supervise
rm -rf $PREFIX/var/log/atlas-runtime/supervise
sv-enable atlas-runtime && sleep 2
sv up atlas-runtime
```
验证：`file $PREFIX/var/service/atlas-runtime/supervise/control` 应输出 "fifo (named pipe)"。

### 教训
此前对 runit supervise 目录的理解有误。supervise/ 目录必须完全由 runsv 进程管理，部署脚本只应创建 service 目录和 run 脚本，不应触碰 supervise/。这与 systemd 的单元文件 + systemctl 模式不同 — runit 的 supervise/ 是运行状态而非配置。
